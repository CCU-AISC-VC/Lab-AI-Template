# 5. 常見問題

## 流程

**Q：每個任務都要寫 PLAN 嗎？改個圖表顏色也要？**
不用。判準是「這次改動會不會影響數值結果」。改顏色、改字體、加註解不用。
只要碰到單位、濾波參數、演算法、資料選取，就要有 PLAN。

**Q：Agent 一直問問題，很煩。**
這是設計如此，好過它安靜地猜。如果同樣的問題被問第二次，代表答案應該寫進 `SPEC.md` 而不是只在對話裡講。
永久性的答案 → `SPEC.md`；只適用這個任務的 → PLAN 的「開始前的三個問題」。

**Q：一次只能改三個檔案，重構的時候不夠用。**
這條的用意是逼你先說明範圍，不是禁止大改動。講清楚要動哪些檔案、為什麼，經同意後就可以做。

**Q：可以跳過階段 1 直接執行嗎？**
可以，但那就是普通的 vibe coding，這個模板對你沒有幫助。

## 資料

**Q：Agent 說找不到資料檔。**
先自己確認檔案真的在 `data/raw/`、檔名大小寫一致。
確認之後如果它還是找不到，多半是路徑寫錯（相對路徑 vs 絕對路徑）。
**絕對不要接受它用範例資料「先示範」。**

**Q：Agent 改到 `data/raw/` 了怎麼辦？**
`data/raw/` 不進 git，所以救不回來。從 NAS 或雲端重新下載，然後檢查是哪條規則沒生效。
預防方式：`chmod -R a-w data/raw/`。

**Q：資料太大不能進 git，怎麼給別人？**
git 只放程式碼、規格與結果。原始資料放 NAS 或雲端，在 `data/README.md` 寫清楚位置與大小。
別人拿到 repo 後照 `README.md` 下載放進 `data/raw/`，就能重跑。

## 結果

**Q：跑出來的數字和上次不一樣。**
依序檢查：隨機種子有沒有固定 → 輸入檔是不是同一批 → `SPEC.md` 的參數有沒有被改過 → 套件版本有沒有變。
這也是為什麼要求「可以重跑的腳本」而不是對話紀錄。

**Q：圖出來了但看不懂在畫什麼。**
退回去要三件事：座標軸的物理量與單位、資料來源檔名、一段文字說明結果代表什麼。
`instructions.md` 第五節階段 3 就是這樣規定的。

**Q：怎麼知道結果是對的，不是看起來對？**
跑 [`04_verification.md`](04_verification.md) 的六項檢查，特別是「極端情況」和「已知解對照」。
在能驗證的案例上先證明程式是對的，再拿去跑不能驗證的真實資料。

## 維護

**Q：`SPEC.md` 改了，之前的結果還算數嗎？**
不算。在 `DEVLOG.md` 記一筆「SPEC 某項變更」，並標註哪些既有結果需要重跑。
這就是 `SPEC.md` 有修訂紀錄表格的原因。

**Q：`DEVLOG.md` 越來越長。**
不要整理、不要刪。它的價值就在於完整。要找東西用搜尋。

**Q：學弟妹接手要給他什麼？**
repo 網址 + 原始資料位置。`README.md` → `instructions.md` → `SPEC.md` → `DEVLOG.md` 這條路徑應該能讓他自己上手。
如果不行，代表這四份檔案有一份沒寫好。

## 工具

**Q：換 agent（Claude → Copilot → Cursor）要重寫規則嗎？**
不用，這就是把規則放在 `instructions.md` 而不是各家設定檔的原因。各家的指向檔只有一行，都在 `repo-template/` 裡。

**Q：用 MATLAB 不是 Python 呢？**
改 `instructions.md` 第二節，`.m` 檔一樣放 `scripts/` 和 `src/`。流程與檢查完全不變。
